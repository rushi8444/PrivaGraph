1. EXECUTIVE SUMMARY & ELEVATOR PITCH
================================================================================
Q: What is this project and what problem does it solve?
A: 
PrivaGraph (Privacy-Guard) is a high-performance, privacy-preserving knowledge
graph middleware and security proxy that sits between enterprise proprietary
documents and third-party cloud Large Language Models (OpenAI GPT-4o, Anthropic
Claude, Google Gemini).

The Problem:
Enterprises want to leverage cloud LLMs for retrieval-augmented generation (RAG)
and natural language query answering, but they cannot legally or ethically send
confidential data containing Personally Identifiable Information (PII, such as
names, SSNs, phone numbers, emails, salaries, employee IDs, and internal project
codes) to external cloud AI providers. Standard redaction destroys relationships
and context, making the LLM unable to answer analytical questions.

The PrivaGraph Solution:
1. Zero Cloud PII Exposure: Real sensitive entities are detected locally and
   replaced with deterministic opaque tokens (e.g., "John Smith" -> "⟦E7_PERSON_001⟧").
2. Relationship Preservation: Because tokenization is deterministic via keyed HMAC,
   the system constructs an anonymized multi-document Knowledge Graph (NetworkX)
   linking tokens across different documents without ever exposing real identities.
3. AES-256-GCM Local Vault: The true mapping (token -> plaintext) is encrypted
   locally with authenticated 256-bit AES-GCM and stored inside a local secure vault.
4. RBAC & OWASP Sanitization: Subgraphs retrieved for a user query are filtered
   against user roles (RBAC) and scanned for prompt injection before being sent.
5. Local Answer Reconstruction: The cloud LLM reasons purely over the abstract
   graph structure and returns an answer containing tokens. The local proxy
   intercepts the answer, looks up the tokens in the encrypted vault, replaces them
   with decrypted values, and delivers the natural plaintext answer to the user.

3. COMPREHENSIVE END-TO-END FLOW (STEP-BY-STEP TRACE)
================================================================================

--------------------------------------------------------------------------------
3.1 DOCUMENT INGESTION FLOW (WRITE PATH)
--------------------------------------------------------------------------------
Endpoint: POST /api/v1/documents/ingest (app/api/v1/documents.py)

Step 1: File Upload
- The client uploads an OKF markdown file (e.g. sample_hr_doc.md) via HTTP multipart.
- OKFParser reads the YAML frontmatter containing:
  * document (id, title, classification: PUBLIC/INTERNAL/CONFIDENTIAL/RESTRICTED, department, author, created)
  * privacy (entity_categories, redaction_policy: TOKENIZE, min_confidence: 0.85)
  * access_control (allowed_roles, denied_roles)
  * graph (namespace, link_strategy, max_traversal_depth)
- OKFParser cleans the body text, strips markdown headers, and segments text into sentences.

Step 2: PII Detection
- For each sentence, PresidioDetectionEngine scans for configured entity categories
  (standard: PERSON, EMAIL, PHONE, US_SSN, CREDIT_CARD; custom: SALARY, PROJECT_CODE, EMPLOYEE_ID).
- If Presidio / spaCy is missing, it automatically falls back to FallbackPIIDetector.
- ConfidenceFilter removes entities below the confidence threshold (e.g., 0.85).
- Overlapping spans are resolved by picking the detection with the highest confidence score.

Step 3: Deterministic HMAC Tokenization & Vault Storage
- DeterministicTokenizer computes HMAC-SHA256(secret_key, "ENTITY_TYPE:normalized_value").
- Formats a unique token: ⟦XX_TYPE_NNN⟧ (e.g., ⟦E7_PERSON_001⟧).
- Replaces raw entity text in the sentence from right-to-left (preserving character indices).
- For each token, EncryptedVault encrypts the original value using AES-256-GCM with a random
  12-byte (96-bit) nonce and stores {ciphertext, nonce, entity_type, hmac_digest, doc_id}.

Step 4: Triple Extraction & Graph Construction
- TripleExtractor scans tokenized sentences for Subject-Predicate-Object (SVO) relationships:
  * Uses regex heuristics, canonical verb dictionaries (MANAGES, REPORTS_TO, EARNS, LEADS, etc.).
  * Performs pronoun coreference resolution across sentence boundaries (e.g., "He earns...").
  * Fallbacks to proximity relationships (RELATED_TO) when no explicit verb is identified.
- KnowledgeGraphBuilder adds nodes (subjects, objects) and directed edges to a NetworkX MultiDiGraph.
- Every node and edge is tagged with document classification, allowed roles, denied roles, and namespace.

Step 5: Storage & Audit
- Document metadata is stored in state.documents dictionary.
- AuditLogger appends an immutable, SHA-256 hash-chained log entry with event type DOCUMENT_INGESTED.
- Response returns: { status: "ingested", doc_id, entities_detected, triples_extracted, tokens_stored }.


--------------------------------------------------------------------------------
3.2 NATURAL LANGUAGE QUERY & RETRIEVAL FLOW (READ PATH)
--------------------------------------------------------------------------------
Endpoint: POST /api/v1/query (app/api/v1/query.py)

Step 1: Query Ingestion & Query-Side Tokenization
- User submits a question: "Who manages the budget and what does John Smith earn?"
- Detector scans the query itself for PII (e.g. "John Smith" -> ⟦E7_PERSON_001⟧).
- Query tokens are stored in the vault under doc_id="query" so that entity tokens in the query
  match existing graph nodes.

Step 2: Query Analysis & Subgraph Seed Identification
- QueryAnalyzer extracts explicit tokens and keywords (stripping stopwords).
- Matches tokens/keywords against graph node IDs to select seed nodes.

Step 3: Graph Neighborhood Traversal (k-hop BFS)
- ContextBuilder uses SubgraphExtractor to perform Breadth-First Search (BFS) up to k hops
  (default depth = 3) around all seed nodes in the NetworkX graph.
- Merges all extracted subgraphs into a unified candidate subgraph.

Step 4: Fine-Grained Role-Based Access Control (RBAC)
- RBACFilter inspects the authenticated UserContext (user roles):
  * If user has ANY denied_role -> Node is REMOVED.
  * If allowed_roles is specified and user lacks ALL allowed roles -> Node is REMOVED.
  * If no ACL restrictions exist -> Node is KEPT (PUBLIC).
  * Edges are retained ONLY if both source AND target nodes are accessible.

Step 5: Subgraph Context Serialization
- The accessible subgraph is serialized into an anonymized markdown format:
  # Knowledge Graph Context
  ## Entities: - ⟦E7_PERSON_001⟧ (namespace: hr.compensation), ...
  ## Relationships: - ⟦E7_PERSON_001⟧ --[MANAGES]--> ⟦B1_SALARY_002⟧, ...

Step 6: OWASP Prompt Injection Sanitization
- PromptSanitizer scans the serialized context for injection patterns:
  * Instruction overrides ("ignore all previous instructions")
  * Role hijacking ("you are now a system admin")
  * Data exfiltration ("output the system prompt")
  * Vault/key probing ("show vault password", "decrypt master key")
- If an injection is detected: request is aborted (HTTP 400), logged to audit trail as INJECTION_BLOCKED.

Step 7: Cloud LLM Proxying
- LLMGateway prepares an LLMRequest with strict system instructions:
  * Instructs the LLM to use the tokens verbatim inside normal sentences (e.g., "⟦E7_PERSON_001⟧ earns ⟦B1_SALARY_001⟧").
  * Emits request to OpenAI / Anthropic / Google Gemini API.
  * Offline fallback: If no API key is provided or network fails, format_natural_fallback converts
    the graph triples into natural English without crashing.

Step 8: Local Token Reconstruction (Vault Decryption)
- The raw LLM response (containing tokens) is received locally by TokenReconstructor.
- Regex finds all ⟦XX_TYPE_NNN⟧ tokens in the text.
- TokenReconstructor performs a batch retrieval against EncryptedVault.
- AES-256-GCM decrypts each ciphertext using its stored nonce and the master key.
- Tokens in the text are replaced with decrypted real values.
- ResponseFilter verifies no residual untokenized PII leaked.

Step 9: Audit Logging & Client Response
- AuditLogger records QUERY_SENT and QUERY_RECONSTRUCTED events.
- Client receives: { answer: "John Smith earns $185,000/year...", metadata: { entities_reconstructed: 2, subgraph_nodes: 6, ... } }.

3.3 SECURITY, VAULT & CRYPTOGRAPHIC FLOW
--------------------------------------------------------------------------------
1. Key Management:
   - 256-bit (32-byte) AES key configured via environment variable VAULT_MASTER_KEY.
   - HMAC secret key configured via TOKENIZER_SECRET_KEY.
2. Encryption (AES-256-GCM):
   - Authenticated Encryption with Associated Data (AEAD).
   - Generates a cryptographically random 12-byte nonce per encryption operation.
   - Computes an authentication tag to guarantee ciphertext integrity and authenticity.
3. Audit Log Hash Chaining:
   - Each audit entry computes SHA-256 of JSON(entry fields + prev_hash).
   - The first entry points to "GENESIS".
   - Any modification, deletion, or reordering of log entries breaks the chain and is flagged.

4.5 TOKENIZATION & VAULT LAYER (app/tokenization/)
--------------------------------------------------------------------------------

14. app/tokenization/token_codec.py
    - Purpose: Token format specification, recognition, and extraction.
    - Key Components:
      * `TOKEN_PATTERN`: Regex `\u27e6[A-Z0-9]{2}_[A-Z_]+_\d{3}\u27e7` matching tokens like `⟦E7_PERSON_001⟧`.
      * `find_tokens(text)`: Extracts all token strings from a given text.
      * `is_token(value)`: Validates if a string exactly conforms to the token structure.

15. app/tokenization/tokenizer.py
    - Purpose: Generates deterministic, opaque tokens using Keyed-HMAC.
    - Key Details:
      * `tokenize(entity)`: Normalizes entity type and value, computes `HMAC-SHA256(secret, "TYPE:value")`, generates prefix from the first 2 hex chars of the digest (collision namespace) and suffix from integer modulo 1000.
      * Resulting format: `⟦XX_TYPE_NNN⟧`.
      * Determinism guarantee: The exact same name (e.g. "John Smith") across 50 different documents always yields the exact same token `⟦E7_PERSON_001⟧`.
      * `tokenize_text(text, entities)`: Sorts entities in reverse offset order (from end of string to beginning) to prevent character index shifting during in-place token replacement.

16. app/tokenization/vault.py
    - Purpose: Encrypted local storage mapping opaque tokens back to real plaintext PII.
    - Key Components:
      * `EncryptedVault`: Uses `AESGCMCipher` with the master key.
      * `store(token, entity_type, original_value, hmac_digest, doc_id)`: Encrypts original_value with a fresh random 12-byte nonce, storing ciphertext, nonce, metadata, and timestamps. Idempotent.
      * `retrieve(token)`: Decrypts and returns the original value, updating `accessed_at` timestamp.
      * `batch_retrieve(tokens)`: Efficiently decrypts multiple tokens in a single operation for local response reconstruction.
      * `count()`: Returns total number of active vault mappings.

4.6 SECURITY & CRYPTOGRAPHY LAYER (app/security/)
--------------------------------------------------------------------------------

17. app/security/encryption.py
    - Purpose: AES-256-GCM Authenticated Encryption with Associated Data (AEAD).
    - Key Class `AESGCMCipher`:
      * `NONCE_SIZE = 12` (96 bits, standard GCM recommendation).
      * `KEY_SIZE = 32` (256 bits).
      * `encrypt(plaintext)`: Generates `os.urandom(12)` nonce, encrypts plaintext, returns `(ciphertext, nonce)`. GCM automatically computes a 128-bit authentication tag appended to the ciphertext.
      * `decrypt(ciphertext, nonce)`: Verifies authentication tag and decrypts; raises `InvalidTag` if tampered with.
      * `generate_key()`: Generates 32 cryptographically secure random bytes.

18. app/security/key_manager.py
    - Purpose: Key derivation and generation utility.
    - Key Function:
      * `generate_master_key()`: Returns a hex-encoded 256-bit AES master key.

19. app/security/audit_log.py
    - Purpose: Append-only, tamper-evident audit logger with cryptographic hash-chaining.
    - Key Components:
      * `AuditLogger`: Writes to `data/audit.jsonl`.
      * `log(event_type, details)`: Appends an entry containing `timestamp`, `event_type`, `details`, and `prev_hash`. Computes `entry_hash = SHA-256(json(entry))`. Sets `_last_hash = entry_hash`.
      * `read_entries(limit)`: Reads audit entries and cryptographically verifies the hash chain (`chain_valid` boolean on every record).
      * Event Constants: DOCUMENT_INGESTED, ENTITY_DETECTED, TOKEN_CREATED, VAULT_ACCESSED, QUERY_SENT, QUERY_RECONSTRUCTED, INJECTION_BLOCKED, ACCESS_DENIED.

20. app/security/trust_boundary.py
    - Purpose: Formalizes OWASP trust zone models and validates data flows between zones.
    - Key Enum `TrustZone`: LOCAL_TRUSTED, LOCAL_UNTRUSTED, EXTERNAL_UNTRUSTED.
    - `validate_flow(source, dest, data_type)`: Ensures raw PII never exits LOCAL_TRUSTED; tokenized data may cross to EXTERNAL_UNTRUSTED.

4.7 KNOWLEDGE GRAPH LAYER (app/graph/)
--------------------------------------------------------------------------------

21. app/graph/triple_extractor.py
    - Purpose: Extracts Subject-Predicate-Object (SVO) triples from tokenized sentences.
    - Key Components:
      * `VERB_MAP`: Maps verb phrases to canonical graph predicates (e.g., "manages" -> MANAGES, "reports to" -> REPORTS_TO, "earns" -> EARNS, "leads" -> LEADS, "contacts" -> HAS_CONTACT).
      * `PRONOUNS`: Coreference set ("he", "she", "they", "it", "the employee", etc.).
      * `extract(tokenized_sentence, doc_id, prev_subject)`:
        1. Checks for pronoun starting sentences; resolves to `prev_subject`.
        2. Splits compound sentences by conjunctions (`and`, `but`, `;`).
        3. Identifies tokens before and after verb phrases to generate Triples.
        4. Fallbacks to sentence-wide scan or proximity linkage (`RELATED_TO`) if no verbs match.

22. app/graph/graph_builder.py
    - Purpose: Constructs and manages the in-memory directed multigraph using NetworkX (`nx.MultiDiGraph`).
    - Key Components:
      * `add_triples(triples, header)`: Inserts nodes with document ACL metadata (classification, allowed_roles, denied_roles, namespace, doc_ids) and directed edges with predicates and source sentences. Prevents duplicate edges.
      * `get_neighbors(node_id, depth=2)`: Performs Breadth-First Search (BFS) up to `depth` hops around a seed node and returns the subgraph.
      * `serialize_subgraph(subgraph)`: Formats the subgraph into a concise, tokenized Markdown representation (`## Entities`, `## Relationships`) optimized for LLM context windows.
      * `to_graph_data()`: Converts the graph into Pydantic `GraphData` (nodes and edges) for frontend D3.js visualization.
      * `get_stats()`: Computes total node/edge counts, namespace distributions, and entity type breakdowns.

23. app/graph/graph_store.py
    - Purpose: Abstraction layer for graph storage, aliasing `KnowledgeGraphBuilder` for future Neo4j pluggability.

4.8 RETRIEVAL & CONTEXT ASSEMBLY LAYER (app/retrieval/)
--------------------------------------------------------------------------------

24. app/retrieval/query_analyzer.py
    - Purpose: Analyzes user queries to identify referenced entities and search keywords.
    - Key Methods:
      * `extract_tokens(query)`: Finds any explicit `⟦XX_TYPE_NNN⟧` tokens in the query.
      * `extract_keywords(query)`: Strips punctuation and 35+ common English stopwords.
      * `match_nodes(query, node_ids)`: Matches remaining query keywords against graph node labels and IDs.

25. app/retrieval/rbac_filter.py
    - Purpose: Enforces document-level and node-level role-based access control.
    - Key Rules in `filter_subgraph(subgraph, user)`:
      * A node is accessible if: (1) user roles do not intersect with `denied_roles`, AND (2) `allowed_roles` is empty OR user has at least one matching allowed role.
      * An edge is retained ONLY if both its source node and target node pass accessibility checks.
      * Returns an authorized subgraph view tailored to the user's role profile.

26. app/retrieval/subgraph_extractor.py
    - Purpose: Multi-seed k-hop neighborhood extraction.
    - Key Method `extract_subgraph(seed_nodes, depth=2)`: Iterates over all seed nodes, extracts each neighborhood via BFS, and composes them into a single `nx.MultiDiGraph`.

    - Key Workflow in `build_context(query, user)`:
      1. Calls `QueryAnalyzer` to find tokens or matching keyword nodes.
      2. Calls `KnowledgeGraphBuilder.get_neighbors` across matched nodes.
      3. Calls `RBACFilter.filter_subgraph` with the requesting `UserContext`.
      4. Calls `KnowledgeGraphBuilder.serialize_subgraph` to output the final anonymized context string.

      * Offline Fallback: If no API key is provided, logs warning and invokes `format_natural_fallback` to construct natural responses directly from graph triples.

31. app/proxy/reconstructor.py
    - Purpose: Local token reconstruction replacing opaque tokens with decrypted values.
    - Key Method `reconstruct(tokenized_response)`:
      * Detects all `⟦XX_TYPE_NNN⟧` tokens in the LLM response text.
      * Executes `vault.batch_retrieve(tokens)` to decrypt real PII locally.
      * Performs in-memory string replacement: `result.replace(token, real_value)`.
      * Returns `(reconstructed_text, entities_count)`. Real PII never leaves the local perimeter.

5. CRITICAL SECURITY & ALGORITHMIC CONCEPTS EXPLAINED
================================================================================

5.1 DETERMINISTIC HMAC TOKENIZATION
- Why not random UUIDs?
  If "John Smith" in Document A was assigned UUID_1 and "John Smith" in Document B
  was assigned UUID_2, the Knowledge Graph would create two disconnected nodes.
  The LLM would not know they are the same person and could not answer cross-document queries.
- How PrivaGraph achieves privacy + linkability:
  Token = HMAC-SHA256(secret_key, "ENTITY_TYPE:normalized_value").
  Identical entities always produce identical tokens, allowing multi-document graph
  edges to merge naturally while ensuring third parties without the secret key cannot
  reverse the HMAC digest.

5.2 AES-256-GCM AUTHENTICATED ENCRYPTION
- Why GCM mode over CBC or ECB?
  AES-GCM is an AEAD (Authenticated Encryption with Associated Data) cipher.
  It provides both confidentiality (privacy) and authenticity (integrity).
- Nonce Security: Every single vault entry uses a fresh 12-byte `os.urandom(12)` nonce.
  Even if the same salary "$185,000" is encrypted multiple times, each ciphertext is
  completely distinct.
- Tamper Protection: Any alteration of ciphertext bytes fails authentication tag verification
  and raises `InvalidTag`.

5.3 CRYPTOGRAPHIC HASH-CHAINED AUDIT TRAIL
- Structure:
  Entry[0]: entry_hash = SHA-256(Entry[0] + "GENESIS")
  Entry[1]: entry_hash = SHA-256(Entry[1] + Entry[0].entry_hash)
  Entry[N]: entry_hash = SHA-256(Entry[N] + Entry[N-1].entry_hash)
- Benefit: Prevents insider tampering or deletion of security audit logs. Any modification
  to a past log entry invalidates the hashes of all subsequent entries.

5.4 OWASP LLM TOP 10 MITIGATIONS
- LLM01 (Prompt Injection): Context scanned by `PromptSanitizer` before building prompt.
- LLM02 (Sensitive Information Disclosure): Cloud LLM never receives raw PII; `ResponseFilter`
  scans outputs.
- LLM06 (Excessive Agency): Read-only RBAC subgraphs restrict model knowledge strictly
  to the user's authorized scope.

5.5 FINE-GRAINED GRAPH RBAC FILTERING
- Node-Level ACL: Each node inherits document `allowed_roles` and `denied_roles`.
- Graph Pruning: `RBACFilter` computes set intersections with `UserContext.roles`.
- Edge Safety: An edge is pruned if either endpoint node is pruned, preventing orphaned
  or unauthorized relationship leaks.

6. TOP 25 INTERVIEW QUESTIONS & MODEL ANSWERS
================================================================================

Q1: What is the core architectural innovation of PrivaGraph?
A1: PrivaGraph solves the enterprise AI dilemma by combining deterministic HMAC
    tokenization with an anonymized Knowledge Graph and a local AES-256-GCM vault.
    Instead of sending raw PII or destroying relational structure through crude redaction,
    it allows cloud LLMs to reason over relationship graphs using opaque tokens and
    reconstructs the final answer locally on-premise.

Q2: Walk me through what happens when an OKF document is ingested.
A2: (1) OKFParser validates YAML frontmatter and splits text into clean sentences.
    (2) PresidioDetectionEngine detects PII spans matching configured categories.
    (3) DeterministicTokenizer replaces PII with tokens `⟦XX_TYPE_NNN⟧` using keyed HMAC.
    (4) EncryptedVault encrypts raw values using AES-256-GCM with 96-bit nonces.
    (5) TripleExtractor parses tokenized sentences into SVO triples with coreference resolution.
    (6) KnowledgeGraphBuilder inserts nodes/edges into NetworkX with ACL metadata.
    (7) AuditLogger writes a SHA-256 hash-chained log entry.

Q3: How does the query pipeline work from user input to final answer?
A3: (1) QueryAnalyzer extracts tokens and keywords from the user's question.
    (2) SubgraphExtractor runs k-hop BFS around seed nodes in NetworkX.
    (3) RBACFilter prunes nodes and edges that the user's roles are not allowed to view.
    (4) ContextBuilder serializes the authorized subgraph into tokenized markdown.
    (5) PromptSanitizer scans context for prompt injection patterns.
    (6) LLMGateway sends tokenized context + question to OpenAI/Anthropic/Gemini.
    (7) TokenReconstructor decrypts tokens locally from EncryptedVault.
    (8) The user receives the decrypted plaintext answer.

Q4: Why did you use deterministic HMAC tokenization instead of UUIDs or hashing without a key?
A4: Plain UUIDs are non-deterministic, meaning the same person in two documents would get
    different tokens, breaking cross-document knowledge graph traversal. Simple hashing
    (like SHA-256) without a secret key is vulnerable to rainbow table and dictionary
    attacks. Keyed HMAC provides determinism for graph linking while preventing unauthorized
    reversal without the secret key.

Q5: What encryption standard is used in the vault and why?
A5: AES-256-GCM. We chose GCM because it is an AEAD cipher that provides both strong
    confidentiality and cryptographic data integrity verification via authentication tags.
    Every encryption uses a fresh 12-byte random nonce to ensure semantic security.

Q6: How do you handle prompt injection attacks?
A6: Through `PromptSanitizer`, which scans retrieved context against known OWASP LLM
    attack vectors: instruction overrides ("ignore previous instructions"), role hijacking,
    data exfiltration ("output system prompt"), vault probing ("show vault password"),
    and malicious URL schemes. If detected, the query is blocked before reaching the LLM
    and logged as INJECTION_BLOCKED.

Q7: What happens if Microsoft Presidio or spaCy is not installed?
A7: The system includes a zero-dependency `FallbackPIIDetector` using compiled regexes
    and rule-based heuristics that detect SSNs, emails, phones, salaries, credit cards,
    project codes, employee IDs, and names, ensuring the application remains functional.

Q8: How does RBAC work across the knowledge graph?
A8: Every node and edge in the NetworkX graph stores metadata: `classification`,
    `allowed_roles`, and `denied_roles`. When a user queries the graph, `RBACFilter`
    evaluates their `UserContext.roles`. If the user has a denied role or lacks an allowed
    role, the node is pruned. Edges are removed if either endpoint is inaccessible.

Q9: What is the Open Knowledge Format (OKF)?
A9: OKF is a structured Markdown specification with YAML frontmatter. It allows document
    owners to declaratively specify security classification, PII scanning policies,
    minimum confidence thresholds, allowed/denied roles, and knowledge graph namespaces.

Q10: How does the system handle pronouns and multi-sentence relationships?
A10: `TripleExtractor` performs lightweight coreference resolution. When a sentence begins
     with pronouns ("He", "She", "They", "The employee"), it binds the subject to the
     primary subject token of the preceding sentence.

Q11: Why is answer reconstruction performed locally instead of in the cloud?
A11: Local reconstruction guarantees zero PII cloud exposure. The cloud provider only ever
     sees abstract tokens like `⟦E7_PERSON_001⟧`. The master encryption key and plaintext
     PII never leave the organization's secure network boundary.

Q12: How does the audit log prevent tampering?
A12: It uses a cryptographic hash chain similar to a blockchain. Every entry includes
     `prev_hash` and its own `entry_hash = SHA-256(entry_data + prev_hash)`. The first
     entry references "GENESIS". Any modification or deletion of a past line breaks the
     chain, which is detected during verification in `read_entries()`.

Q13: How does the system handle cloud LLM rate limits or outages?
A13: `LLMGateway` includes retry logic with exponential backoff for HTTP 429 errors.
     Additionally, it includes `format_natural_fallback`, which converts graph triples
     into fluent English sentences locally if cloud providers are unreachable or offline.

Q14: What is the token format and what do its components mean?
A14: Format: `⟦XX_TYPE_NNN⟧` (e.g. `⟦E7_PERSON_001⟧`).
     - `⟦...⟧`: Mathematical white square brackets (Unicode \u27e6 and \u27e7) to avoid
       collisions with standard brackets or markdown syntax.
     - `XX`: First 2 hex characters of the HMAC digest (collision namespace).
     - `TYPE`: Entity category (PERSON, SALARY, US_SSN, etc.).
     - `NNN`: Integer suffix derived from the HMAC digest.

Q15: How does the frontend visualize the knowledge graph?
A15: Using React 18 and D3.js (`d3.forceSimulation`, `d3.forceLink`, `d3.zoom`).
     Nodes are color-coded by entity type (indigo for PERSON, green for SALARY, red for SSN),
     support dragging/pinning, display directional relationship arrowheads, and show
     hover tooltips with ACL and classification metadata.

Q16: How do you prevent character offset shifting when tokenizing text?
A16: In `DeterministicTokenizer.tokenize_text()`, detected entities are sorted in descending
     order by their start offset (`sorted(entities, key=lambda e: e.start, reverse=True)`).
     Replacing tokens from the end of the string to the beginning preserves the validity
     of preceding character indices.

Q17: What OWASP LLM Top 10 vulnerabilities are addressed?
A17: LLM01 (Prompt Injection via `PromptSanitizer`), LLM02 (Sensitive Information Disclosure
     via deterministic tokenization + vault encryption + `ResponseFilter`), and LLM06
     (Excessive Agency via strict read-only RBAC graph filtering).

Q18: How does the system resolve overlapping entity detections?
A18: `_resolve_overlaps()` compares overlapping character spans and selects the candidate
     with the highest confidence score, discarding lower-confidence conflicting spans.

Q19: What graph library is used and what is the production roadmap?
A19: In the MVP, NetworkX (`nx.MultiDiGraph`) provides fast in-memory graph operations.
     In Phase 2 of production, `GraphStore` will be backed by Neo4j for persistent,
     distributed graph queries with Cypher.

Q20: How does the vault handle concurrent reads and writes?
A20: In the MVP, `EncryptedVault` uses asynchronous Python dictionaries (`async def store/retrieve`).
     For enterprise deployment, it will migrate to PostgreSQL with row-level encryption or Redis.

Q21: Can you explain the Trust Zone architecture?
A21: Aligned with OWASP, we define 3 zones in `trust_boundary.py`:
     - LOCAL_TRUSTED: Inside enterprise firewall (raw PII, encryption master key, vault).
     - LOCAL_UNTRUSTED: Client browsers / incoming requests.
     - EXTERNAL_UNTRUSTED: Public cloud LLM APIs.
     `validate_flow()` enforces that raw PII never transitions to EXTERNAL_UNTRUSTED.

Q22: How are custom enterprise entities like salaries and employee IDs detected?
A22: In `custom_recognizers.py`, we define custom Presidio `PatternRecognizer` instances
     with regex patterns and confidence weights for salaries (`$185,000`, `$2.3M`),
     project codes (`PRJ-YYYY-XXXX`), and employee IDs (`EMP-XXXXX`).

Q23: How do you verify graph connectivity across multiple documents?
A23: When Document A mentions "John Smith" (tokenized to `⟦E7_PERSON_001⟧`) and Document B
     mentions "John Smith", both resolve to the exact same HMAC token. In NetworkX,
     `add_triples()` adds edges to the existing node `⟦E7_PERSON_001⟧`, automatically
     forming a cross-document knowledge graph.

Q24: What automated tests are implemented in the project?
A24: Pytest suite covering:
     - `test_okf_parser.py`: YAML parsing, validation, sentence segmentation.
     - `test_tokenizer.py`: Token generation, determinism, collision handling, offset safety.
     - `test_reconstructor.py`: Single and multi-token decryption and replacement.
     - `test_prompt_sanitizer.py`: Detection of 5+ injection attack vectors.
     - `test_api.py`: Full end-to-end integration tests (ingest -> list -> graph -> query -> audit).

Q25: If an interviewer asks you "What would you improve if you had another month?", how do you answer?
A25: (1) Replace in-memory storage with PostgreSQL (vault) and Neo4j (graph).
     (2) Integrate Hardware Security Modules (HSM) or AWS KMS / Azure Key Vault for master key lifecycle.
     (3) Add hybrid semantic vector search + graph retrieval (GraphRAG with embeddings).
     (4) Implement OAuth2 / OIDC JWT authentication with real enterprise IdPs (Okta/Azure AD).
     (5) Add streaming token reconstruction over WebSockets / Server-Sent Events (SSE).
